# 향후 아이디어와 보류 결정

2026-10-23 사용자 결정. 현재 앱은 소규모 동료 테스트 중이며, 아래 항목은 V0.2.3에 구현하지 않는다.

## 찜 제거

찜은 원래 커플 앱에서 가져온 방 공용 값(`places.favorite`)이다. 이번에는 동작·표시·데이터를 유지한다.
그룹 앱에서는 개인 찜과 헷갈리므로 향후에는 기능을 없애는 방향을 우선 검토한다.
실행 시 목록 탭·하트·검색/상태 처리·읽기 전용 검사·DB 칸과 과거 데이터의 정리를 함께 검토한다.
개인 찜으로 바꾸는 것은 현재 결정이 아니다.

## 메일 시스템과 비밀번호 찾기

현재는 메일 없는 아이디 계정이므로 비밀번호 분실 기능을 새로 만들지 않는다.
아주 나중에 메일 발송 시스템과 실제 이메일 연결·인증을 구현할 때, 검증된 이메일로 비밀번호를 재설정하는 흐름을 함께 만든다.
기존 가상 이메일 계정을 실제 사용자 이메일과 연결하는 이전 절차도 필요하다.

## 피드백

문제 보내기 버튼은 현재 필요하지 않다. 동료 피드백은 기존 연락 경로로 받는다.

## 사용자 화면에 없는 3일 보관함 (설계 검토만)

삭제를 클릭하면 즉시 파일을 지우는 대신 DB에서 `deleted_at`, `purge_after = deleted_at + interval '3 days'`를 기록한다.
사용자 목록·검색·직접 조회·공개 RPC·사진 URL 발급에서 제외한다. 사용자가 보관함을 열거나 복원하는 화면은 만들지 않는다.

이 방식은 사용자 요청에서 DB 삭제와 Storage 삭제를 분리해 현재의 부분 실패를 줄인다.
**3일이 지난다는 사실만으로 삭제 오류가 사라지는 것은 아니다.** 다음 조건이 필요하다.

1. 숨김 처리와 삭제 작업 등록을 한 DB 트랜잭션으로 처리한다. 작업에는 사진 원본·썸네일 경로를 저장한다.
2. 사용자 RLS와 사진 저장소 권한도 삭제 예정 항목을 제외한다. 화면 필터만으로 숨기는 것은 불충분하다.
   기존에 발급한 사진 주소·브라우저/서버 캐시는 즉시 취소되지 않으므로, 노출 종료까지 허용할 시간을 정하고 필요하면 중계에서 상태를 재확인한다.
3. 홈 서버의 systemd timer가 만료한 작업을 집어 처리한다. 서버가 꺼져 있으면 다음 기동 시 밀린 작업을 처리한다.
4. 사진 삭제 → 성공 확인 → 최종 DB 삭제 순서로 처리한다. 이미 없는 파일은 성공으로 보고, 실패한 작업은 남겨 재시도한다.
5. 일부 파일만 지워진 뒤 재시작해도 이어갈 수 있게 작업 상태·재시도 횟수·마지막 오류를 보관한다. 작업자 중복 실행도 막는다.
6. 장소뿐 아니라 개별 사진 삭제·마지막 멤버의 방 삭제도 같은 규칙으로 묶는다. 숨긴 동안의 용량과 경로 참조를 유지한다.

사용자에게는 3일 동안 보이지 않지만 서버에는 남아 있다는 점을 삭제 안내에 적는다.

## 백업 보관 장소

서버 PC에 Supabase DB 덤프와 사진 파일을 보관해도 된다. 실행 중인 복제 DB보다는 날짜별로 복원 가능한 백업 묶음을 우선한다.
동기화로 삭제까지 그대로 따라가거나 최신 파일 하나만 덮어쓰면 과거 오류를 복구하기 어렵다.

| 방법 | 장점 | 한계 |
|---|---|---|
| 홈 서버 내부 디스크에 날짜별 백업 | 추가 장비 없이 자동화·빠른 복원이 쉬움. 운영 DB는 Supabase에 있어 별도 복사본이 됨 | 서버 디스크 고장·계정 침해로 로컬 백업을 함께 잃을 수 있음 |
| 외장 USB SSD/HDD에 백업 | 서버 내부 디스크 고장에 대한 분리, 용량 확장·분리 보관 가능 | 상시 연결하면 서버와 함께 손상될 수 있음. 연결·마운트·디스크 건강 확인 필요 |

권장 구성은 **Supabase 운영 데이터 + 홈 서버 일별 백업 + 분리 보관하는 외장 디스크 주간 복사**다.
둘 중 하나만 고른다면 외장 디스크를 백업 전용으로 쓰는 편이 디스크 고장에 대한 분리가 낫다.
사진을 USB로 옮겨 직접 서비스하는 '운영 보조 저장소'는 백업과 역할이 다르며, 현재 Supabase Storage 구조를 바꾸는 별도 작업이다.

백업에는 DB의 앱 스키마·데이터뿐 아니라 계정 복구에 필요한 Auth 범위, 사진 실파일, 복구에 필요한 설정을 포함해야 한다.
자격 증명은 코드 저장소나 일반 로그에 넣지 않고 암호화·접근 제한한다. 실제 복원 시험으로 포함 범위를 확인한다.
자동 백업·디스크 설정은 이번에 설치하지 않았다.

근거: [Supabase DB 백업](https://supabase.com/docs/guides/platform/backups)은 Storage 실파일을 포함하지 않는다.
[Supabase 로컬 복원](https://supabase.com/docs/guides/local-development/restoring-downloaded-backup),
[NCSC의 오프라인 백업 설명](https://www.ncsc.gov.uk/blog-post/offline-backups-in-an-online-world)을 함께 참고한다.
