## 1. 한 줄 요약과 목표

**공개 방은 "자랑하고 싶은 우리 지도"를 앱 가입자들이 읽기 전용으로 둘러보는 기능이다. 데이터는 홈 서버가 정해진 항목만 골라 주고, Supabase 권한(RLS)은 넓히지 않는다.**

목표
- 친구 커플이 "서울 라멘 지도" 같은 목록 하나를 다른 친구들에게 보여 줄 수 있다.
- 지금 쓰는 개인 방과 그 안의 데이터는 하나도 바뀌지 않는다.
- 공개해도 위험하지 않다. 방문 날짜, 아이디, 초대 코드처럼 사람을 추적하거나 방에 들어올 수 있게 하는 정보는 나가지 않는다.
- Supabase 무료 한도(트래픽 월 5GB, 조직 전체가 같이 씀)를 넘지 않는다. 둘러보는 사람에게 내주는 사진에는 **월 1GB까지만** 쓴다(8장).

이렇게 나눠서 설명한다.
- 개인 방: "우리끼리 쓰는 기록". 일기, 가고 싶은 곳, 우리만 아는 메모.
- 공개 방: "자랑하고 싶은 우리 지도". 예: 서울 라멘 지도, 제주 3박 4일 맛집, 성수 카페 투어.

커플이 진짜 기록은 개인 방에 두고, 보여 주고 싶은 목록 하나만 작은 공개 방으로 따로 만드는 쓰임을 기대한다.

## 2. 이미 정한 것 (주인 결정)

| # | 결정 | 이 문서에서 지키는 방식 |
|---|---|---|
| 1 | 방을 만들 때 공개/개인을 고르고, 나중에 바꿀 수 없다 | DB에서도 바꿀 수 없게 막는다(트리거). 지금 있는 방은 모두 개인 방이 된다 |
| 2 | 로그인 뒤 방 선택 화면의 돋보기로 공개 방을 찾아 읽기 전용으로 들어간다 | 검색과 보기는 로그인한 사람만 쓸 수 있다 |
| 3 | 공개 방에 멤버로 들어올 때 내용이 공개될 수 있다고 알린다. 사진과 후기도 공개된다 | 동의하지 않으면 서버가 참여를 막고, 동의한 시각을 기록한다 |
| 4 | 사용자는 지금 친구 커플 2–4쌍이고, 나중에 더 열 수도 있다. 광고와 돈은 없다 | 지금 규모에 맞게 범위를 작게 잡는다. 더 열기 전에 다시 볼 것은 따로 적었다 |

결정과 부딪히는 아이디어는 표에서 **안 함**이나 **나중**으로 두고, 가장 가까운 안전한 방법을 적었다.
- 기존 개인 방을 공개로 바꾸기: 결정 1과 부딪힌다. 새 공개 방을 만들고 장소를 옮겨 담는다.
- 방장이 위급할 때 공개를 끄기: 결정 1과 부딪힌다. 관리자가 검색과 보기에서 숨기는 것(`public_hidden_at`)으로 대신한다. 공개 방이 개인 방으로 바뀌지는 않는다.
- 로그인 없이 링크로 보기: 결정 2는 검색을 로그인 뒤에 두었다. v0.2.0에서는 링크도 로그인해야 열린다.

### 흐름 A. 공개 방 만들기
1. 방 선택 화면, 방 바꾸기 시트, 또는 첫 화면에서 [새 방 만들기]를 누른다.
2. 방 이름과 닉네임을 넣는다.
3. 공개 범위 카드에서 고른다. (●) 개인 방 "멤버만 볼 수 있어요" / ( ) 공개 방 "앱을 쓰는 누구나 둘러볼 수 있어요". 아래에 "만든 뒤에는 바꿀 수 없어요."
4. 공개 방을 누르면 카드가 펼쳐진다.
   - 이름 칸 예시가 "예: 서울 라멘 지도"로 바뀐다.
   - 소개(선택, 60자, 예: "둘이 먹어 본 서울 라멘집 모음")
   - 안내 상자: "공개 방에서는 장소·사진·후기·별점·닉네임을 앱을 쓰는 누구나 볼 수 있어요. 방문 날짜는 월까지만 보여요. 아이디와 초대 코드는 보이지 않아요. 화면 캡처는 막을 수 없어요."
   - [ ] 이해했어요
   - 공개 방 한도(정할 것 9)에 걸리면 공개 카드를 회색으로 두고 이유를 한 줄로 보여 준다: "공개 방은 한 사람당 1개까지 만들 수 있어요" / "공개 방은 7일에 1개 만들 수 있어요(N일 뒤 가능)" / "지금은 공개 방을 더 만들 수 없어요". 개인 방은 그대로 만들 수 있다.
5. 체크하면 [공개 방 만들기]가 켜진다. `create_room(닉네임, 이름, 'public')`이 실행되고, DB가 한도를 다시 확인한 뒤 `public_key`와 방장의 동의 기록을 저장한다(화면이 늦게 알아도 DB가 막는다).
6. 메인 화면으로 간다. 방 이름 옆에 "공개" 표시가 붙고, "공개 방을 만들었어요." 알림이 뜬다. 첫 멤버 안내 띠에는 [둘러보기 링크 (보기만)]과 [초대 코드 (함께 쓸 친구만)], 그리고 "초대 코드를 받은 사람은 멤버로 들어와 장소를 고치고 지울 수 있어요. 보기만 할 사람에게는 링크를 보내 주세요."
7. 장소를 1곳 이상 담으면 검색에 나온다.

### 흐름 B. 공개 방 찾기
1. 방 선택 화면 "어느 방으로 갈까요?" 오른쪽 위의 🔍를 누른다. 방 바꾸기 시트 머리에도 있고, 방이 없을 때는 "공개 방 둘러보기" 링크가 있다. 처음 한 번은 아래에 "다른 사람들의 공개 방을 둘러볼 수 있어요"가 보인다.
2. 둘러보기 화면: [‹] "공개 방 둘러보기", 검색 칸 "방 이름·소개로 찾기", "공개 방 N곳 · 최근 활동순"
3. 글자만 있는 카드 목록이 나온다. 입력하면 바로 걸러진다.
   - 결과 없음: "'라멘'과 맞는 공개 방이 없어요. 다른 낱말로 찾아보세요."
   - 공개 방 없음: "아직 공개 방이 없어요" + [새 방 만들기](이미 방이 3개면 숨김)
   - 실패: "지금은 공개 방을 불러올 수 없어요. 잠시 후 다시 시도해 주세요." + [다시 시도]
4. 카드를 누른다. 내 방이면 평소처럼 들어가고(`switchRoom`), 아니면 흐름 C로 간다.

### 흐름 C. 읽기 전용으로 보기
1. 위에 고정 띠 "둘러보는 중 · 읽기 전용 [닫기]"
2. 머리: 방 이름(⌄ 없음), "공개" 표시, 소개, 멤버 칩(색 점과 닉네임, 방장 표시 없음), 장소 수
3. 탭: 다녀온 곳(기본, 평점순) / 가 보고 싶은 곳 / 찜. 카테고리와 검색도 쓸 수 있다. 장소 추가 버튼, 톱니, 트로피는 없다.
4. 장소를 누르면 상세가 열린다. 썸네일 사진(누르면 큰 사진), 카테고리, 주소 [복사], [지도에서 보기], "방문 3번"과 방문 카드("2026년 10월"), 멤버별 후기(색 줄, 닉네임, ★, 글), "민수가 2026년 9월에 담음"(나간 사람이면 "예전 멤버가 담음"). 메모는 보이지 않는다(정할 것 3). **[최종: 배치는 멤버 상세와 같고(주소 복사 버튼은 따로 두지 않음), 함께 쓰는 메모는 보인다. 찜 하트와 찜 탭은 없다. 머리 오른쪽에 "내 방에 담기"]**
5. [닫기]나 안드로이드 뒤로 가기를 누르면 둘러보기 목록으로 돌아간다. 검색어와 스크롤은 그대로다. 링크로 바로 들어왔으면 둘러보기 목록이 없으므로 마지막으로 쓰던 내 방으로, 그 기록이 없으면 방 선택 화면으로, 방이 하나도 없으면 첫 화면으로 간다. 마지막 방 기록은 바뀌지 않는다.
6. 보는 사이에 방이 숨겨지거나 지워지면: 다음 불러오기에서 404 → "이 공개 방을 찾을 수 없어요" 화면으로 바꾸고 목록으로 돌아간다. 사진이 깨지면(파일이 지워짐) 빈 칸 대신 회색 자리 표시를 둔다.

### 흐름 D. 공개 방에 참여할 때 안내
1. 앱 안: [코드로 참여] → 코드와 닉네임 → [참여하기] → `POST /api/join`
2. 서버가 코드, 이미 멤버인지, 5명이 찼는지, 내 방이 3개인지를 먼저 본다. 걸리면 지금과 같은 오류("방이 가득 찼어요" 등)를 동의 시트 없이 바로 보여 준다. 다 통과했고 공개 방인데 동의가 없으면 409를 보낸다(시도 횟수에 넣지 않는다). 이미 그 방 멤버면 동의 없이 그 방으로 보낸다(지금처럼).
3. 동의 시트 "공개 방이에요"
   > '서울 라멘 지도'는 앱을 쓰는 누구나 둘러볼 수 있는 방이에요. 이 방에 남기는 장소·사진·후기와 닉네임 '지훈'이 공개돼요. 나가면 내 후기는 지워지지만, 내가 담은 장소와 사진은 방에 남아요.
   >
   > 공개 방 닉네임에는 실명 대신 별명을 추천해요.

   [동의하고 참여] / [취소]
4. 동의하면 다시 보낸다. 참여와 함께 동의 시각과 문구 버전이 `public_room_acks`에 저장되고, "공개 방에 들어왔어요." 알림이 뜬다. 취소하면 코드가 그대로 채워진 입력 화면으로 돌아간다.
5. 가입하면서 들어올 때: 가입 양식 → 서버가 **계정을 만들기 전에** 코드·5명 여부를 보고(`space_code_open`) 공개 방이면 409를 보낸다 → 같은 시트에서 [동의하고 가입] → 계정 생성과 참여 → "가입했어요. 공개 방에 들어왔어요." 동의와 계정 생성 사이에 방이 가득 차면 지금처럼 "가입은 됐지만 방에 들어가지 못했어요"로 안내한다(빈 계정이 남는 드문 경우).

### 흐름 E. v0.2.0을 내는 날, 지금 사용자
지금 방은 모두 개인 방이 되고 겉모습도 그대로다(표시가 붙지 않는다). 한 번만 알림: "새 기능: 공개 방. 지금 방은 그대로 개인 방이에요. 방 선택 화면이나 방 이름(⌄)의 돋보기로 둘러볼 수 있어요."

### 흐름 F. 공개 방에서 나가기와 마지막 멤버의 방 삭제
1. 다른 멤버가 남는 경우: 나가기 확인에 공개 방 문구(3-5)를 더한다. 나가면 지금처럼 내 후기·월드컵 기록·후기 없는 내 방문이 지워지고, 내가 담은 장소와 사진은 남아 "예전 멤버"로 공개된다. 방장이 나가면 가장 먼저 들어온 남은 멤버가 방장이 되어 소개를 고칠 수 있다. 동의 기록은 남겨 둔다(남은 장소·사진이 공개되는 근거).
2. 마지막 멤버인 경우: 확인 문구 "이 공개 방과 둘러보기 링크가 사라져요. 되돌릴 수 없어요." → 지금처럼 `begin_room_delete`(썸네일 경로도 함께 돌려준다) → 화면이 사진과 썸네일 파일을 지움 → `leave_room`.
3. `begin_room_delete` 순간부터 공개 API는 그 방을 404로 본다(`deleting_at`). 다만 서버 캐시 때문에 목록과 방 JSON이 **최대 2분** 더 보일 수 있고, 그 사이 사진은 파일이 지워져 깨진다(흐름 C 6번). 화면이 중간에 실패해 15분이 지나면 방이 되살아나는데, 이때 일부 사진이 빠진 채 다시 공개된다(지금 개인 방과 같은 성질). `public_key`는 무작위라 다른 방에 다시 쓰이지 않는다.
4. 지워진 공개 방은 계정당 공개 방 수에서 빠지지만, 생성 간격(7일)은 그대로 적용된다(만들고 지우기를 되풀이하지 못하게).

### 흐름 G. 계정이 없는 사람이 링크를 받았을 때
1. `/r/<key>`를 열면 로그인 화면이 나오고 위에 "공개 방을 보려면 로그인해야 해요. 계정은 초대 코드로만 만들 수 있어요."가 보인다. 방 이름은 보여 주지 않는다(로그인 전에는 키를 풀지 않는다, OG 카드도 일반 카드).
2. 초대 코드가 있으면 가입한 뒤 같은 기기에서 그 방이 바로 열린다(sessionStorage의 키). 없으면 링크를 보낸 친구에게 코드를 받으라는 안내만 한다. 공개 방 키로는 가입할 수 없다.

### 경계 상황 정리
| 상황 | 처리 |
|---|---|
| 멤버가 공개 방을 나감 | 흐름 F 1. 담은 장소·사진은 "예전 멤버"로 남는다. 사진을 내리고 싶으면 나가기 전에 지우라고 안내한다(자동 숨김은 v0.2.x, 정할 것 12) |
| 마지막 멤버가 방을 지움 | 흐름 F 2–4. 최대 2분 캐시, 15분 참여 막힘 |
| 공개 방이 5명이 됨 | 둘러보기는 그대로 된다(보는 사람은 인원에 들지 않는다). 코드로 들어오려는 사람은 동의 시트 전에 "방이 가득 찼어요". 검색 카드에는 "멤버 5명"만 쓰고 "가득 참"은 쓰지 않는다(참여 신청이 없으므로 의미가 없다) |
| 초대 코드가 인터넷에 퍼짐 | 5명이 차면 더는 못 들어온다. 그 전에 모르는 사람이 들어와 고치거나 지우면 관리자가 `public.sh kick`·`rotate`로 대응한다(3-4, 정할 것 20) |
| 계정이 없는 사람 | 흐름 G. 아무것도 볼 수 없다 |
| 보는 중에 방이 숨겨짐·지워짐 | 흐름 C 6. 이미 내준 사진 URL은 만료될 때까지(썸네일 1시간, 큰 사진 10분) 열린다. 급하면 관리자가 그 사진 파일을 지운다 |
| 검색 남용 | 검색어는 폰 안에서만 쓰여 서버에 가지 않는다. 목록·보기 API는 횟수 제한으로 막고, 공개 방 전체를 긁어 가는 것은 "공개"의 범위로 본다. 다만 사진은 한 사람이 하루 한도를 혼자 다 쓰지 못하게 사람별 한도를 둔다(8장) |
| 공개 방 한도에 닿음 | 흐름 A 4번의 문구. 개인 방은 계속 만들 수 있다 |
| 둘러보는 중에 노트북이 꺼짐 | 다음 요청이 실패하고 "지금은 공개 방을 불러올 수 없어요 [다시 시도]". 이미 받은 화면과 썸네일은 그대로 보인다. 페이지를 새로 열면 사이트 자체가 안 열린다(6장 표) |
| 사진 한도가 다 참 | 사진 없이 글만 보내고 "오늘은 사진 보기가 멈췄어요" 띠. 멤버가 자기 방에서 보는 사진은 영향 없음 |
| 장소가 아주 많은 공개 방 | 방 JSON은 장소 300곳까지 한 번에 보내고, 넘으면 최근 활동순 300곳 + "앱에서는 300곳까지만 보여요" (나누어 받기는 나중) |

### 휴대폰 화면 기준 (360–390px)
- 가로 스크롤 없음, 양옆 16px. 카드는 88px 이상, 이름과 소개는 2줄까지, 숫자 줄은 한 줄에 말줄임.
- 읽기 전용 띠 40px, [닫기] 누르는 영역 44px. 360px에서도 줄바꿈하지 않는다.
- 공개 범위와 동의 카드는 화면 너비 전체, 선택 영역 44px 이상. 다크 모드 색은 지금 있는 토큰을 쓴다.
- dev/mock에 장면을 더한다(공개 범위 선택, 참여 동의, 가입 동의, 빈 목록, 결과, 둘러보기 메인·상세, 사진 한도 초과). 라이트·다크 모두, 390px 기준.

## 5. 공개되는 것 / 절대 공개 안 되는 것

| 구분 | 공개 (로그인한 앱 사용자에게) | 공개 안 됨 |
|---|---|---|
| 방 | 이름, 소개, 멤버 수, 장소 수, 최근 활동(며칠 전 / 월) | 방 uuid, 초대 코드, 만든 사람(`created_by`), 만든 시각 |
| 멤버 | 닉네임, 색. 응답마다 들어온 순서로 매기는 임시 번호(m1–m5)로 구분하고, 나간 사람은 번호 없이 "예전 멤버"로 묶는다. 번호는 응답 안에서만 쓰는 것이라 누가 나가면 바뀌어도 된다 | 사용자 id, 로그인 아이디, 이메일 형태 아이디, 방장 표시, 들어온 날짜, 이 사람이 있는 다른 방 |
| 장소 | 이름, 카테고리, 주소, 지도 링크, 가고 싶은 곳/다녀온 곳 상태, 찜 표시, 담은 달과 담은 사람(번호) **[최종: 찜 표시 빼고, 함께 쓰는 메모 넣음]** | 정확한 등록 시각, 함께 쓰는 메모(기본값, 정할 것 3) **[최종: 찜 표시]** |
| 방문·후기 | 방문한 달(YYYY-MM), 멤버별 별점과 후기 글 | 정확한 방문 날짜, 수정 시각 |
| 사진 | 장소마다 최대 몇 장(정할 것 7), 썸네일 먼저, 서버가 서명한 짧은 URL(썸네일 1시간, 큰 사진 10분) | 원본 경로, 업로드 시각(파일 이름을 무작위로 바꿔 없앤다), EXIF/GPS(업로드할 때 이미 지워진다) |
| 월드컵 | — (v0.2.0) | 기록과 도장 |
| 비공개 방 | — | 이름, 개수, 존재 여부까지 전부 |

원칙
- 서버 함수가 정해진 항목만 골라 JSON을 만든다(`select *` 안 씀). 날짜는 SQL 안에서 월로 자르기 때문에 정확한 날짜는 DB 밖으로 나가지 않는다.
- 사용자 id를 방마다 다른 번호로 바꿔서, 같은 사람이 두 공개 방에 있어도 이어 붙일 수 없게 한다.
- 시험으로 지킨다: 응답의 키 목록이 정해진 목록과 정확히 같은지, 응답 문자열에 사용자 uuid·초대 코드·아이디 이메일이 없는지 검사한다.

## 6. 기술 구조 요약

### 데이터 모델 (새 SQL `public_rooms.sql` + 되돌리기 SQL) **[최종: 파일 이름 `supabase/public.sql`·`public_rollback.sql`, 함수 목록은 public-rooms-design.md §2]**
| 바뀌는 곳 | 내용 |
|---|---|
| `couples.visibility` | `'private'`(기본) / `'public'`, CHECK. 바꾸면 오류를 내는 BEFORE UPDATE 트리거 |
| `couples.public_key` | 공개 방에만 있는 10자 키, 부분 unique 인덱스. 공개 방일 때만 null이 아니라는 CHECK |
| `couples.description` | 60자까지, 기본값 `''` |
| `couples.public_hidden_at` | 관리자 숨기기. 앱에는 권한을 주지 않는다 |
| 새 표 `public_room_acks` | `couple_id, user_id, kind('create'\|'join'), version, acked_at`. 동의 기록. `couple_members`에 두면 나갈 때 줄과 함께 지워져서, 남은 장소·사진이 공개되는 근거가 사라진다. 그래서 따로 두고 나가도 지우지 않는다. 방이 지워져도 남겨 생성 간격(7일) 확인에 쓴다(방 FK 없음). service_role만 접근. 계정 삭제가 생기면 그때 같이 지운다 |
| `place_photos.thumb_path` | 320px 썸네일 경로(비워도 됨) |
| 함수 | `create_room`, `set_room_description`, `join_room_for`, `space_code_info`, `public_room_list`, `public_room_view`, `public_rooms_version()`, 관리자용 `admin_room_kick`, `admin_room_rotate_code`(service_role만) |
| 저장소 정책 | 사진 select/insert/delete 세 정책에 `is_couple_member(p.couple_id)`를 직접 넣는다 |

`public_room_*` 함수는 `security definer`, `search_path = ''`이고, 실행 권한은 service_role에만 준다(anon과 authenticated에서는 거둔다). 기존 `create_couple`과 `join_couple_for`는 이름과 인자를 그대로 둔다. `create_couple`은 개인 방만 만들고, `join_couple_for`는 공개 방을 거부한다. 그래서 SQL을 먼저 적용해도 옛 서버가 그대로 돌아간다.

### 읽기 API (홈 서버, 새 모듈 `deploy/home/public.cjs`)
- `GET /api/public/rooms`: 목록, 최대 50개
- `GET /api/public/rooms/:key`: 방 하나. 키 형식이 틀리면 DB를 부르지 않고 404, 비공개·숨김·삭제 중인 방도 404. 장소는 300곳까지
- `GET /r/<key>`: index.html을 그대로 내준다(API가 아니라 화면 경로. 키는 화면이 로그인 뒤 API로 푼다)
- 순서: 스위치(`PUBLIC_ROOMS`)와 준비 여부 확인 → Bearer 토큰 확인(`/api/join`과 같은 방식, 토큰→uid는 60초 캐시) → 횟수 제한 → 캐시 → service_role로 RPC → 서버가 허용 목록을 한 번 더 거른다 → 사진 서명 → 응답
- **RLS는 넓히지 않는다.** 이유: 저장소 insert/delete 정책은 "장소 행이 보이는지"만 확인한다. 공개 방 장소를 다른 사용자에게 보이게 하면 그 사람이 공개 방 사진을 올리고 **지울 수도 있게** 된다. `couples` 행을 보이게 하면 초대 코드, 곧 쓰기 권한이 드러난다. anon이든 로그인 사용자든 똑같다.

### 검색
v0.2.0은 목록을 한 번 받아 폰에서 거르는 방식만 만든다. 전체 공개 방 한도(약 30개)가 있는 동안 서버 검색은 필요 없다. 한도를 풀고 50개를 넘게 되면 서버 ILIKE 검색으로 바꾸고(이스케이프, 낱말 AND, 400ms 디바운스, 한글 조합 중에는 보내지 않음, 이전 요청 취소), pg_trgm은 수천 개가 되었을 때 생각한다.

### 사진
- **업로드할 때 썸네일**: 지금 있는 `shrink()`로 320px JPEG(약 20–30KB)를 하나 더 만들어 `<place_id>/t/` 아래에 둔다. 같은 폴더 아래라 저장소 정책이 그대로 적용된다. 공개 방은 v0.2.0부터 새로 생기므로 모든 사진에 썸네일이 있다. 썸네일 만들기가 실패한 사진은 둘러보기에서 큰 사진 대신 자리 표시를 둔다(원본을 목록에 내보내지 않는다). 기존 개인 방 사진에 썸네일을 채우는 일은 공개 방과 상관없어서 v0.2.x로 미룬다.
- **지우는 길을 모두 고친다**: 사진 삭제, 장소 삭제, 나가기, 방 삭제(`begin_room_delete`가 돌려주는 경로), 되돌리기 SQL. 빠뜨리면 1GB 저장소에 고아 파일이 쌓인다.
- **파일 이름을 무작위로**: 지금은 `<place_id>/<Date.now()>-<i>.jpg`라서 서명 URL에 업로드 시각(밀리초)이 드러난다. `crypto.randomUUID()`로 바꾼다.
- **서명은 서버가**: 썸네일은 1시간짜리로 묶어서 서명하고, 남은 시간이 30분 이상이면 같은 URL을 다시 쓴다(브라우저 캐시가 맞는다). 큰 사진은 누를 때만, 10분짜리로 그때그때 서명한다. 서명 URL은 앱 밖으로 옮겨 붙여도 만료 전까지 몇 번이고 받을 수 있어서, 무거운 큰 사진일수록 짧게 둔다. `loading="lazy"`
- 멤버 쪽도 이득이다. 멤버 화면 목록도 썸네일을 쓰게 바꾸면(썸네일이 있는 사진만) 사진 트래픽이 약 8–10배 준다. 지금은 목록에서도 1080px 원본(150–300KB)을 받는다.

### 캐시 (4GB 노트북 기준)
메모리 LRU 약 8MB(서비스 메모리 한도 256MB 안에서). 방 JSON 120초, 목록 60초, 서명 URL은 30분 이상 남았으면 다시 쓴다. 응답 헤더는 `private, max-age=60`. 로그인이 필요하므로 Cloudflare 에지 캐시는 쓰지 않는다. 숨기기는 SQL로 DB만 바꾸므로 서버는 알 수 없다. 그래서 `public.sh hide|kick|rotate`는 DB를 바꾼 뒤 서비스를 다시 시작해 캐시를 비운다(몇 초 끊김). SQL Editor로 직접 숨기면 최대 2분 뒤에 반영된다. 이미 내준 사진 URL은 다시 시작해도 만료 전까지 열린다.

### 횟수 제한
`createLimiter`를 다시 쓴다. 사용자별·IP별로 방 보기 분당 30회, 목록 분당 20회, 전체 분당 300회. 넘으면 429. 같은 Wi-Fi 친구들이 함께 둘러봐도 IP별 분당 30회면 넉넉하다. 로그에는 경로와 결과만 남긴다(검색어, 키, uid, 토큰은 남기지 않는다). 누가 어떤 방을 봤는지는 기록하지 않는다.

사진 한도 카운터(8장)는 횟수 제한과 달리 **파일에 저장**한다(1분마다, KST 날짜·월별 합계와 사람별 오늘 합계). 메모리에만 두면 서비스가 죽었다 살아날 때마다 한도가 처음부터 다시 시작된다. 사람별 합계는 uid 대신 해시로 두고 다음 날 지운다.

### 그 밖
- 모든 응답에 `X-Robots-Tag: noindex, nofollow`. `/r/<key>`에는 일반 OG 카드만 낸다(방 이름과 사진은 넣지 않는다).
- 남의 방 글이 내 화면에 뜨므로 XSS 영향이 커진다. 둘러보기 화면의 모든 출력이 `esc()`와 `safeUrl`을 거치는지 정적 시험을 둔다. CSP 헤더는 v0.2.x.
- 서버 시작 시 `public_rooms_version()`이 있는지 확인하고, 없으면 공개 API를 끈다.
- 화면의 공개 방 상수(`PUBLIC_ROOMS_ENABLED`)는 `SIGNUP_ENABLED`처럼 서버가 index.html을 내줄 때 바꿔 넣는다. 스위치가 꺼졌거나, 비밀 키 확인이나 `public_rooms_version()` 확인이 실패하면 false로 내서 돋보기·공개 범위 카드·공개 표시를 숨긴다(이미 있는 공개 방의 멤버 기능은 그대로).

## 8. 비용과 한도

| 자원 | 한도 | 공개 방 영향 | 대책 |
|---|---|---|---|
| Supabase 트래픽 | 월 5GB, 조직 전체가 함께 씀(하루 약 170MB) | 썸네일이 없으면 사진 있는 장소 30곳 목록 한 번에 약 6MB, 800번쯤 보면 한 달 치가 다 나간다 | 썸네일(목록 약 0.6–0.9MB), 글자만 있는 검색 카드, 큰 사진은 누를 때만 |
| 공개 방 사진 예산 | 월 1GB(조직 전체 5GB의 20%) | 인기 방 하나나 한 사람이 예산을 다 쓰는 것을 막는다 | **월 1GB에서 거꾸로 정한다**: 하루 약 33MB → 썸네일 800개(약 20MB) + 큰 사진 60개(약 12MB). 사람별로는 하루 썸네일 200개·큰 사진 20개. 월 합계가 1GB에 닿으면 그 달 끝까지 멈춘다. 넘으면 사진 없이 보내고 "오늘은 사진 보기가 멈췄어요. 내일 다시 보여요." 멤버가 자기 방에서 보는 사진은 세지 않는다. **세는 법**: 서명한 수가 아니라 둘러보는 사람에게 보낸 응답에 URL을 넣은 횟수를 센다. 캐시 때문에 같은 URL이 여러 사람에게 가므로, 서명 수만 세면 실제보다 적게 센다. 응답에 넣은 횟수는 브라우저 캐시 덕에 실제보다 많게 세므로 안전한 쪽으로 틀린다. 앱 밖으로 옮겨진 URL은 셀 수 없어서 만료 시간을 짧게 둔다(6장 사진) |
| JSON 트래픽 | — | 방 하나를 계속 봐도 120초 캐시라 하루 최대 720번, 약 72MB(최악, 방 JSON 100KB 기준). 방이 30개면 이론상 최악은 하루 2GB지만, 실제로는 한 방을 하루 종일 2분마다 보는 일이 없다 | 캐시, 횟수 제한. 서버가 하루 JSON 전송량도 세어 두고 200MB를 넘으면 로그에 경고를 남긴다 |
| 저장소 | 1GB | 썸네일로 약 15% 늘어난다 | 지우는 길을 모두 고친다 |
| DB | 500MB | 새 칸 몇 개 정도, 거의 늘지 않는다 | — |
| 노트북 | 4GB, 서비스 256MB | 캐시 8MB, 요청 조금 | 캐시와 제한. 사진은 Supabase에서 바로 받는다 |
| 돈 | 0원 | 광고·결제 없음 | 무료 범위에서만 |
