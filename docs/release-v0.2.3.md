# V0.2.3 안정화 (2026-10-23)

대상은 소규모 동료 테스트 중인 그룹 앱이다.

## 반영한 내용

- 지도 자동완성을 기다리는 동안 방·계정이 바뀌면 장소 저장을 중단한다. 쓰기 대상은 저장 시작 시 방·사용자로 고정한다.
- 일반 장소 추가도 이름·주소를 정리해서 같은 장소가 있으면 확인한다. 의도적으로 같은 장소를 추가하는 것은 허용한다.
- 공개 방 썸네일 요청이 실패하면 25분짜리 성공 캐시를 남기지 않는다. 상세를 다시 열면 재시도할 수 있다.
- `stability.sql`: 사진 등록 시 장소 행을 잠그고 최대 10장을 DB에서 검사한다. 기존에 10장을 넘긴 장소의 사진은 삭제하지 않는다.
- `save_visit_review(uuid,date,uuid,numeric,text)`: 기존 RLS를 따르는 SECURITY INVOKER 함수. 장소별로 잠그고 같은 날짜 방문을 재사용한다.
  내 후기만 추가·수정·삭제한다. 날짜 변경과 후기 저장은 한 트랜잭션이므로 후기 저장 실패 시 날짜 변경도 되돌린다.
- `/healthz`는 프로세스 응답, `/readyz`는 설정한 가입·공개 방 기능의 준비 상태다. 필요한 SQL이 빠지면 `/readyz`는 503이다.
  의도적으로 secret key 없이 가입·공개 방을 모두 끈 배포는 200이다. 응답에는 상태만 있고 키·프로젝트 주소는 없다.
- 배포 스크립트는 `/readyz`와 실제 화면을 확인한 뒤 성공으로 판단한다. 새 SQL이 빠져 기능이 꺼진 배포는 이전 코드로 되돌린다.
- 앱 소개와 공개 방 예시를 그룹용 문구로 정리했다. `couples` 등 DB 이름과 서버 서비스·경로 이름은 그대로 둔다.

## 기존 프로젝트 적용

1. 운영 DB 변경 전 별도 백업과 복원 경로를 확보한다. DB 덤프와 사진 파일은 각각 보관해야 한다.
2. `public.sql`이 적용된 프로젝트에서 **`supabase/stability.sql`을 한 번** 실행한다.
3. SQL Editor에서 `select public.stability_schema_version();`이 1인지 확인한다(관리자 역할).
4. 수정한 소스를 검토·커밋한 뒤 기존 `deploy.ps1`로 배포한다. 이 스크립트는 작업 폴더가 아니라 마지막 커밋을 배포한다.
5. `/readyz`가 200이고 계정 설정에 `v0.2.3-261023-8b7c2`가 표시되는지 확인한다.
6. 서로 다른 두 계정으로 같은 장소·같은 날짜 후기를 남겨 방문 하나에 후기가 합쳐지는지, 11번째 사진은 거절되는지 확인한다.

새 프로젝트의 앱 SQL 순서는 `schema.sql` → `friends-keepalive.sql` → `friends-signup.sql` → `groups.sql` → `colors.sql` → `public.sql` → `stability.sql`이다.

## 되돌리기

먼저 앱 코드를 V0.2.1 등 이전 릴리스로 되돌린 다음 `supabase/stability_rollback.sql`을 실행한다.
장소·방문·후기·사진 데이터는 삭제하지 않고, 추가 함수·트리거만 제거한다.
`public_rollback.sql`까지 실행하려면 그 전에 `stability_rollback.sql`을 실행해야 한다.

## 이번에 변경하지 않은 것

- 장소·사진 삭제 동작. 3일간 사용자 화면에서 숨긴 뒤 서버가 정리하는 안은 [향후 아이디어](future-ideas.md)에 정리했다.
- 찜 기능, 비밀번호 분실 대응, 피드백 버튼, 운영 백업 설치. 사용자의 이번 결정에 따라 구현하지 않는다.

## 검증

서버 회귀 테스트, PGlite SQL 테스트, 실제 화면 소스를 실행하는 VM 테스트를 사용한다.
VM 테스트는 지도 조회 취소·방 전환, 중복 확인 취소·계속, 썸네일 오류 후 재시도를 검사한다.
PGlite는 트랜잭션 원복·RLS·사진 수 제한·SQL 되돌리기를 검사한다. 실제 Supabase 동시 연결과 휴대폰 검증은 배포 후 별도로 수행한다.
